# Changelog

All notable changes to `pushery/ses-inbound-mail-for-laravel` are documented here. The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/), and the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

A release carries only the sections that have an entry, in this order: `### ⚠️ Breaking`, `### ✨ Added`, `### 🔧 Changed`, `### ⚡ Performance`, `### 🐛 Fixed`, `### 🔒 Security`, `### 🧹 Deprecated`, `### 🗑️ Removed` and `### 📚 Documentation`.

## [0.4.2] - 2026-11-27

### 🐛 Fixed

- **`ses-inbound-mail:setup-aws` without credentials names the keys that belong in front of it.** Run without keys in the environment and without a profile, the AWS SDK asked the metadata service of an EC2 instance, which does not answer outside AWS, and the command ended with an uncaught `CredentialsException`, reported to the error tracker as a fault of the application. It now says that `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` of an administrator belong in front of the command, fails, and reports nothing.
- **The migration that finds `ses_inbound_mails` no longer takes an interrupted table for complete.** On MySQL a `migrate` that stopped between creating the table and creating its unique index on `message_id` left the table without it, and the next run found the table and recorded the migration as done. A notification SNS delivered twice was then recorded twice. Where the table already stands, the migration now checks for the index and stops with a message that names the table and the way to repair it. A table that carries the index, under any name, passes as before.

  **Upgrade:** an installation whose migrations ran through has nothing to do. One whose `migrate` stops at the message adds the index it names, or drops the table if it holds no mail, and runs `migrate` again.

## [0.4.1] - 2026-11-26

### 🐛 Fixed

- **`ses-inbound-mail:reconcile` succeeds on an installation whose transit disk names no bucket.** An S3 transit disk without a bucket, as an installation that receives no mail configures it, made the scheduled command fail every five minutes with a `TypeError` from the S3 adapter. The command now says that no mail can be in transit and succeeds without resolving the disk. A disk that names its bucket is reconciled as before.
- **An inbound mail created without `found_in_transit` reads `false` after `save()`, as its row holds it.** The migration writes the column as `false` where a row does not name it, and the model did not know that default, so an instance created other than through `record()`, by a factory, a test or a host, read `null` until it was loaded again. The model now names the default.
- **A certificate of SNS that cannot be fetched no longer loses the message.** The endpoint answered a message whose signing certificate it could not fetch with 403, as it answers a forged signature, and Amazon SNS never delivers a message again that was answered 403. A mail whose notification needed its certificate while the address of the certificate did not answer, or answered with a server error or 429, was lost. Such a message is now answered 503, which SNS delivers again, and `NotificationRefused` names the reason `certificate unavailable`. An address that answers it has no such certificate, and a signature that does not hold, stay refused with 403.
- **A second install under another table prefix in the same PostgreSQL schema keeps the handover index of the first.** The migration of the index drops whatever stands under its name before it builds it, and the name was the same under every prefix, so the migration of a second install in the same schema dropped the index of the first. On PostgreSQL and SQLite the name now carries the table prefix where the connection sets `prefix_indexes`, as a name Laravel derives does. An install that already ran the migration keeps its index as it is.

### 📚 Documentation

- **The requirements name the versions the package is tested on.** PHP 8.4.27, 8.5.x and 8.6.x, PostgreSQL 18.7 and MySQL 8.4.13, in the README and on the start page of the documentation.

## [0.4.0] - 2026-11-23

### ✨ Added

- **`PruneExpiredCacheKeys` deletes the signing certificates of SNS a database or a file store keeps past their day.** Such a store deletes an expired entry only when its key is read again, so a certificate the package no longer asks for stayed for good. Scheduled with `Schedule::call(PruneExpiredCacheKeys::class)->daily();`, it deletes the expired rows under `ses-inbound-mail:` in the default store and the store of the rate limiter, and the expired files of a file store; Redis, Memcached and every other store that expires entries itself stay untouched. The documentation has a section on it.

- **`PruneExpiredCacheKeys` also prunes behind a `failover` store and a `storage` store.** Both of these Laravel cache drivers leave expired entries behind as a database or a file store does. A failover store writes each entry into the first of its stores that answers, so the command prunes each of its stores once. A storage store lays its files out on a filesystem disk the way a file store does in its directory, and the command deletes the expired files the store named there and leaves every other file on the disk alone.

### 🔧 Changed

- **`symfony/console` is a declared dependency.** `ses-inbound-mail:take-over` escapes the reason a takeover failed with its output formatter. Every Laravel version the package supports installs the component already, so no installation resolves differently.

### 🐛 Fixed

- **`ses-inbound-mail:take-over` prints the reason a takeover failed as it stands.** Symfony's console formatter read a part of it that looks like a style tag as styling and dropped it.

### 📚 Documentation

- **The Boost skill declares its example of a receiver in `App\Mail`.** The class `FileTheDocument` stood in no namespace there, so a copy of it under `app/Mail` was a class the autoloader does not find. It now stands where the receiver on the start page does.

- **The documentation says that the `octane` store of Laravel Octane is out of the pruner's reach.** The store keeps an expired entry in a table of a fixed number of rows, `octane.cache.rows`, until its key is written again or the server restarts, and the scheduler, where the pruner runs, sees an empty store. Once the table is full, writing a new key fails, so the documentation advises against making `octane` the default cache store of an application that runs this package.

## [0.3.0] - 2026-11-20

### ✨ Added

- **`ignoreMigrations(tablesExist: true)` keeps the reconciliation and the prune on the schedule of an application that migrates the package's table itself.** `ignoreMigrations()`, the documented way to publish the migrations and run the copy, took both off the schedule without a word, as for an application without the table: a mail no notification reported stayed in the transit until its lifecycle deleted it after fourteen days, and the rows and originals of the mails handed over outlived the retention. Called without the argument, `ignoreMigrations()` still takes both off.
- **`NoMailOutlivesItsRetentionCheck` fails while a mail keeps its row past its retention.** For an application that runs `spatie/laravel-health` and sets `SES_INBOUND_MAIL_RETENTION_DAYS`, the check fails once a mail handed over still has its row 26 hours after its retention ran out: the day the daily prune takes to come round, and two hours for a prune that is still running. A prune that never runs because the scheduler does not, or one that fails every night, no longer goes unnoticed while the sender and the recipients outlive the retention. A mail the `prunable()` of the application's own model keeps is not counted, and without a retention the check passes.

### 🔧 Changed

- **`setup-aws` has SNS sign the messages of its topic with SHA256.** SNS signs a topic's messages with SHA1 unless the topic says otherwise, and the setup left every topic it created that way. The new item `topic signature` sets the topic's `SignatureVersion` to 2 where it is anything else, and `--check` names a topic that still signs with SHA1 as one that differs. The endpoint takes messages signed under either version, as before.
- **`setup-aws` stops before its first call where its AWS clients stand in another region than the one it sets up.** The bucket takes the location of the S3 client's region, while every ARN of the setup names `SES_INBOUND_MAIL_AWS_REGION`, so an application that binds `AwsClients` in another region now gets an error that names both regions before anything is read or written.
- **`setup-aws` names the commands that create the receipt rule set `inbound` and make it the active one, where the set does not exist.** It stopped with an error that said to create the set by hand and named no command. The error now gives `aws ses create-receipt-rule-set` and `aws ses set-active-receipt-rule-set` for the region of the setup, and says to move the rules of another active rule set into `inbound` first, since SES receives with one active rule set at a time.
- **Rolling back the migration that creates `ses_inbound_mails` refuses while the table holds a mail.** The migration now leaves a table it finds as it is, so the table its rollback would drop can hold the mails an earlier run recorded, and the rollback throws rather than delete them with the table. The rollback of the column `found_in_transit` refuses the same way while the column marks a mail found in transit. Delete the mails first where they can go, or set the column to false where only the mark can.
- **`Support\EnvSwitch` is internal.** 0.2.2 shipped it as public API, for a configuration file that reads an on-off switch through it. The configuration of this package reads no such switch, so the class leaves the public API: an application that calls it keeps working until a later release changes or removes it.

### ⚡ Performance

- **The reconciliation, the health checks and the prune find their mails through an index instead of reading the whole table.** Each of them asks for the mails not handed to the application yet, or for those handed over before a moment, and the table keeps every mail while no retention is set, so every run read all of it, the reconciliation every five minutes and the health checks at every run. **Upgrade:** run `php artisan migrate`. The migration `0001_01_01_000002_add_handover_index_to_ses_inbound_mails_table` adds an index on `handed_over_at` and `taken_over_at` to `ses_inbound_mails`. It is built concurrently on PostgreSQL and in place on MySQL, so the table takes its writes while it is built, and the two updates the takeover makes to every mail write to the new index as well. An application that keeps the migrations in its own `database/migrations` first copies the file there from `vendor/pushery/ses-inbound-mail-for-laravel/database/migrations`, renamed to start with the current date.
- **The reconciliation and the health check read the moment every mail in transit was written from the listing of the bucket, instead of asking for it file by file.** They listed the transit and then sent one more request for each file, and the reconciliation two more for each mail it recorded, so a full transit, as when the takeover hangs, slowed every run of the health check and could stretch a run of the reconciliation past its five minutes. `ses-inbound-mail:take-over <key>`, which lists nothing, still asks the bucket about its one file.

### 🐛 Fixed

- **`InboundMail` names `created_at` and `updated_at` among its properties.** Its docblock listed every column but the two timestamps, so an application whose static analysis checks the columns a query names, as Larastan does with `checkModelProperties`, was told that `where('created_at', …)` on the model names no column.
- **`setup-aws` no longer calls a setup complete while the endpoint refuses the messages of its topic.** The endpoint takes only the topics `SES_INBOUND_MAIL_TOPICS` names, and nothing held that list against the topic the setup creates: a setup run before the list named it left the subscription waiting for a confirmation the endpoint had refused, and a list that lost the topic later passed `--check` unnoticed. The new item `endpoint takes the topic` holds the topic's ARN against the list, and while the list lacks it, a check and a run both fail and name the ARN to add. The documentation shows how the ARN is made of `SES_INBOUND_MAIL_AWS_REGION`, `SES_INBOUND_MAIL_AWS_ACCOUNT` and `SES_INBOUND_MAIL_TOPIC`, and that it is deployed before the setup subscribes the endpoint.
- **The endpoint refuses a message with a list or a map where SNS writes text with 400, instead of failing with 500.** A message from an allowed topic whose signature, signature version, certificate address or one of its signed fields held a list or a map broke the validator of the signatures with an error, so the endpoint answered 500 and reported an exception without logging the refusal or dispatching `NotificationRefused`. Such a message, and one with an empty signature, signature version or certificate address, is now refused as unreadable before the validator sees it, logged and dispatched like every other refusal.
- **A takeover the queue refused no longer keeps the next takeover of its mail from being queued for more than two hours.** The lock that allows one takeover of a mail at a time was taken before the job went to the queue, and kept where the queue threw, for example because its connection was down. Until it expired, after 8460 seconds with the five tries of the default, the reconciliation and `ses-inbound-mail:take-over` answered that the takeover was queued already while nothing waited in the queue. The lock is now given up where the queue refuses the job, and the exception goes on as before.
- **The prune keeps the row of a mail whose original the archive disk would not delete.** A disk that refused the deletion, for example for a missing permission on the bucket, answered without an error under Laravel's default `'throw' => false`, and the row went anyway: the original with the sender and the recipients stayed on the disk, and no row named it any more. The row now stays with its original, the failure is reported, and the next day's prune tries again.
- **A mail recorded and never taken over no longer drops out of the reconciliation and the health check once its original is gone from the transit.** Both saw such a mail only while the transit listed its original, so a takeover that failed until the lifecycle deleted the original after fourteen days turned `NoMailIsStuckInTransitCheck` green on that day, and a transit disk with a `root` of its own, which lists no key the way SES reports it, kept the check green from the first mail. The check now counts such a mail thirty minutes after it was recorded, and `ses-inbound-mail:reconcile` logs a warning with its id and its key, counts it as `lost` and fails, until the original is back under its key or the row is deleted.
- **The reconciliation and `ses-inbound-mail:take-over` no longer call a file in the transit removed while the disk keeps it.** Under Laravel's default `'throw' => false`, a disk that refused a deletion, for example because the keys of the transit may not delete in the bucket, answered without an error, so the copy of a mail taken over before and the file SES writes to test its access counted as `removed`, the reconciliation ended with success, and the health check went on counting that copy as a stuck mail. Such a file now counts as `failed` and fails the reconciliation, and `ses-inbound-mail:take-over` prints the error and fails.
- **A migration that runs a second time over what it added no longer fails.** An application that keeps the migrations in its own `database/migrations` and publishes them again for a later release gets every migration a second time under a new date, and `php artisan migrate` stopped at the first copy on the table `ses_inbound_mails`, which already existed, so the migration the release added never ran. Each migration now looks first for the table, the column or the index it adds, and runs over what it finds without failing and without touching the mails. On PostgreSQL the table and the column are looked for where a query finds the table along the `search_path`, so on a host whose `search_path` lists a schema of its own first the table migration builds no second, empty table there, and the column migration does not fail on the column it added before. The documentation shows the way a later migration takes instead: its file copied from `vendor/pushery/ses-inbound-mail-for-laravel/database/migrations`, renamed to start with the current date, as for the column `found_in_transit` of 0.2.0.
- **The moments of a mail keep their instant on a PostgreSQL session in another time zone.** The model wrote `received_at`, `taken_over_at`, `handed_over_at` and its timestamps as bare readings, which PostgreSQL reads in the session's zone, so a server whose zone was not the application's stored every moment shifted, and the application received the mail with that shifted `receivedAt`. On PostgreSQL they are written with their offset now, and the retention, the reconciliation and the health checks compare in the same form. MySQL is unchanged.

### 🔒 Security

- **The confirmation of an SNS subscription follows no redirect.** It followed Laravel's HTTP client wherever the address of SNS pointed, over `http` as well, and a redirect that was not followed would have passed as a confirmation. It goes to the address of SNS alone now, and an answer of `3xx` fails the confirmation with its status, so the endpoint answers `500` and SNS sends the confirmation again.

### 🗑️ Removed

- **The empty translation catalogs, their publish tag `ses-inbound-mail-lang` and `Support\LanguageFallbackLoader`.** The package writes no text to translate: its console commands, health checks and log messages are English. Yet `lang/` shipped seven catalogs without a single string, `vendor:publish --tag=ses-inbound-mail-lang` and the umbrella tag copied them into the application, and the provider wrapped the application's translation loader in `LanguageFallbackLoader` to let a regional locale fall back to catalogs that had nothing to answer with. The package now ships no catalog, registers no `-lang` tag and leaves the application's translation loader as it is. A copy published under `lang/vendor/ses-inbound-mail` can be deleted. `LanguageFallbackLoader` was public since 0.1.0: an application that wrapped a loader of its own with it copies the class from 0.2.2.

### 📚 Documentation

- **The README says what the engine suites prove, and no more.** It concluded from the runs on PostgreSQL and MySQL 8.4 that the package runs on Laravel Cloud without further setup, while a run against a database server in the test lane is no run on the serverless Postgres of Laravel Cloud. The requirements name the two engines as the ones Laravel Cloud runs, the fact the sentence stood on, and leave the conclusion out.
- **The Boost skill publishes the migrations once, and only after it asks for `ignoreMigrations()`.** Its configure step was a single block that ran the umbrella tag `ses-inbound-mail` and then `ses-inbound-mail-migrations`, above the paragraph that asks for `SesInboundMailServiceProvider::ignoreMigrations(tablesExist: true)`, and Boost hands the skill over as a workflow whose blocks run in order. Followed as written, it published every migration twice under two dates, before the application could stop the package from loading its own. The step now publishes the configuration alone, names the other tags in a table, and publishes the migrations in a block below that paragraph, as the README does.
- **The installation adds the Flysystem adapter the transit disk needs, and `composer.json` suggests it.** The transit is a disk on Laravel's `s3` driver, which Laravel builds from `league/flysystem-aws-s3-v3`, and neither the framework nor the package installs that adapter: an application that followed the installation as written and lacked it failed at its first takeover on a missing class. The README and the documentation now run `composer require league/flysystem-aws-s3-v3 "^3.0"` beside the package.
- **The documentation shows an archive disk and says where the archive has to live.** Once a mail is taken over, the archive holds its only copy, and its default `local` is the disk of the server that took the mail over: on several servers another one does not find the original, and on a platform whose file system a deploy replaces, the original is gone after the next deploy. The documentation shows an archive on a bucket of its own, and the configuration reference and the comment in `config/ses-inbound-mail.php` say that the archive has to be a disk every web server and worker reads and that survives a deploy. The default stays `local`.
- **The configuration reference says what a variable left blank sets.** It keeps the default, as a number below 1 does, except a blank `SES_INBOUND_MAIL_ARCHIVE_DIRECTORY`, which puts the originals at the top of the archive disk, and a blank `SES_INBOUND_MAIL_PREFIX`, which sets no prefix, so SES stores the mails at the top of the bucket.
- **The documentation names what Amazon SES needs before the first mail arrives.** A new section, "Before you start", shows how to verify the domain as an identity of SES, which MX record to publish, `10 inbound-smtp.<region>.amazonaws.com`, and how to create the receipt rule set `inbound` and make it the active one, each with its command. The setup does none of this, and the documentation named neither the verification nor the MX record, so an application set up as described received no mail. The README and the Boost skill point to the section.
- **The documentation says which keys `setup-aws` runs with.** It promised that the setup never ran with the keys of the application, while the AWS SDK takes `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` from the environment ahead of any profile, and Laravel loads the `.env` there: an application whose `.env` names those keys, for Laravel's SES mailer or an S3 disk, ran the setup with them, `AWS_PROFILE` set or not. The documentation, the Boost skill and the docblocks of `AwsClients` and the command now say so, and show the keys of an administrator set in front of the command, which the `.env` does not override.
- **The examples of the README and the documentation run as they are written.** The README set the topics on a shell line of their own, which reached neither `setup-aws` nor the `.env`, named none of the settings the setup reads, and put the receiver and its binding into one block, a fatal error once saved as a file; the documentation declared the receiver without the namespace it was bound under, so the takeover found no class to hand the mail to. The README now writes every setting of the setup into the `.env`, and both show the receiver as `app/Mail/OpenAConversation.php` in `App\Mail`, bound in the `register()` method of a service provider.
- **The start page shows the package at work.** A mail as SES stored it in the transit, and what the application receives once the package has taken it over: the id, the sender and recipients, the verdicts of SES, and where the copy lies with its SHA-256 and size. Both stand under the picture as text too, where a reader can enlarge, search and copy them.
- **The configuration reference names the two settings no environment variable sets, and the limit of an address is given in bytes.** `route.middleware` and `models` are set in the published configuration file alone. An address longer than 320 bytes is left out of the row of every mail, reported or found in the transit; the page spoke of 320 characters, 64 before the `@` and 255 after it, which the package never checked apart, and named the limit under the reconciliation only.

## [0.2.2] - 2026-11-11

### 🐛 Fixed

- **A daily prune that was killed no longer keeps the next day's prune from running.** 0.2.1 locked the prune for 1440 minutes, exactly its interval, so the lock of a prune that died without releasing it lasted until the next prune was due, and that prune was skipped without a word. An application whose schedule guard asks every task for a lock under its interval failed on it as well. The lock now lasts 120 minutes, and a running prune still holds back a second one.

## [0.2.1] - 2026-11-10

### 🐛 Fixed

- **The daily prune of the retention never runs twice at once.** It was planned on one server but without an overlap guard, so a prune that outlasted the day ran beside the next one, both deleting the same rows and originals, and an application whose schedule guard checks every task, the package's included, failed on it. A running prune now holds back the next one, as the reconciliation does.

## [0.2.0] - 2026-11-09

### ✨ Added

- **`ReceivedMail::$foundInTransit` says whether the reconciliation found a mail rather than a notification reporting it.** Such a mail carries the verdicts SES wrote into it and none on SPF, DKIM or DMARC, so an application that treats it differently no longer has to read that off empty verdicts. **Upgrade:** run `php artisan migrate`. The migration `0001_01_01_000001_add_found_in_transit_to_ses_inbound_mails_table` adds the column `found_in_transit` to `ses_inbound_mails`, and a mail recorded before it reads as reported.
- **A retention for the rows and the originals of the mails handed to the application.** `SES_INBOUND_MAIL_RETENTION_DAYS` sets how many days a mail keeps its row, which names its sender and recipients, and its original on the archive disk after its handover. With it set, the package schedules a daily `model:prune` for its model, which deletes both. Without it nothing is deleted, as before.

### 🐛 Fixed

- **A mail the reconciliation finds in transit is handed over for the recipient SES delivered it to, with SES's verdicts on spam and viruses.** The reconciliation read the recipients from `Delivered-To`, `X-Original-To`, `To` and `Cc`, so a mail forwarded to the application's address named only the addresses it came through, and the application found no recipient it knew; and it handed every such mail over without a verdict, as if SES had never checked it. It now takes the recipient from the `for` clause of the `Received` header SES puts on top, and the headers as before only where that clause is missing, and reads `X-SES-Spam-Verdict` and `X-SES-Virus-Verdict`.
- **A mail whose handover to the application failed in every try is handed over again.** Its original had already left the transit, so neither the reconciliation nor the health check saw it, and the mail never reached the application. The reconciliation now queues its takeover once more fifteen minutes after the original was taken over, and the health check counts it while it waits.
- **The health check counts a mail as stuck after thirty minutes in the transit, not fifteen.** Fifteen minutes is when the reconciliation takes a mail, and its next run comes up to five minutes later, so a mail on its ordinary way made the check fail. `Reconciliation::STUCK_AFTER_MINUTES` names the thirty minutes.

## [0.1.0] - 2026-11-08

### ✨ Added

- **An endpoint for the notifications of Amazon SNS.** It takes a message only from a topic of `ses-inbound-mail.topics` and only with a valid signature of SNS, confirms a subscription only at an address of SNS, and refuses everything else with 403, or 400 where it cannot read the message, before it uses anything of it. Every refusal is logged and dispatched as `NotificationRefused`. Its path, host and middleware come from the configuration.
- **The takeover of a mail from transit.** Every mail SES reports gets one row, once per id SES gave it. A queued job copies the original byte for byte onto a disk of the application, reads the copy back and holds its SHA-256 and size against the original, and only then deletes it in transit. The application receives the mail through `ReceivesInboundMail`, again on a later try where it threw. One takeover of a mail is queued at a time, with its lock in the application's default cache store, so the reconciliation queues no second one while the first waits for its next try.
- **The reconciliation, the net under the notifications.** Every five minutes, on one server, `ses-inbound-mail:reconcile` goes through every mail that has waited in transit for more than fifteen minutes, a limit that is the same for every application. A mail no notification reported is recorded with the envelope its headers name, leaving out an address longer than 320 characters, and taken over. A takeover that stopped is queued once more, the copy of a mail that was already taken over and the file SES writes to test its access are removed, and a mail that cannot be handled holds up none of the others. `ses-inbound-mail:take-over <key>` takes one mail by its key, whatever its age. For an application that runs `spatie/laravel-health`, `NoMailIsStuckInTransitCheck` fails while a mail waits past that time.
- **The setup of the receiving path in AWS.** `php artisan ses-inbound-mail:setup-aws` sets up what `ses-inbound-mail.aws` names: the bucket of the transit with Block Public Access, Bucket owner enforced and SSE-S3, its policy that lets SES store only the mail of the application's own receipt rule, its lifecycle, the topic and its policy, the subscription of the endpoint, the receipt rule in the rule set `inbound` the applications of an account share, and an IAM policy that lets the application's user only read, list and delete in the transit. The lifecycle is the same for every application: a mail is deleted after 14 days as a net under the takeover, a version that is no longer the current one after a day, and an upload that never finished after a day. Every item is read first and written only where it differs, so a second run changes nothing, and `--check` writes nothing and fails where an item is missing or differs.
